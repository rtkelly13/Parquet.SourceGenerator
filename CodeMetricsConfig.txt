# Code metrics thresholds for the hand-written code under src/ (docs/21-CODE-METRICS.md, #251).
#
# Read by the CA1502 / CA1505 / CA1506 analyzers (enabled at `warning` for [src/**.cs] in
# .editorconfig; CI's `-warnaserror` promotes them), and re-enforced independently by
# scripts/CodeMetrics.cs so that a typo here cannot silently open a hole.
#
# THIS IS A RATCHET. These numbers come down as the code improves. They are never raised to
# accommodate new code: a violation is a conversation about the code, not about the number.
#
# Format: 'RuleId'(optional 'SymbolKind'): 'Threshold'. The rule fires when the measured value
# exceeds the threshold (CA1505 fires when the maintainability index falls BELOW it).
#
# WARNING — the only valid SymbolKind spellings are the ones below. An unrecognised entry (e.g.
# `NamedType` instead of `Type`) makes the analyzers stop reporting ENTIRELY AND SILENTLY: no
# CA1509 diagnostic is produced. That failure mode is why scripts/CodeMetrics.cs enforces these
# same numbers from its own computation.

# Cyclomatic complexity per method. 25 is the .NET default, pinned here so an SDK update cannot
# move the gate. Mark Seemann's recommended maximum is 7 (Miller's 7 +/- 2); this is 3.6x that,
# and the two methods that exceed even 25 today are grandfathered by name in TargetParser.cs.
CA1502: 25

# Maintainability index. Fires below 10. The worst member in the repository today is 14
# (TargetParser.CollectMembers), so this gate has four points of headroom and is live, not vacuous.
CA1505: 10

# Class coupling. .NET defaults, pinned. Worst today: 61 for a type (TargetParser) and 40 for a
# method (TargetParser.GetTargetModelCore). The method gate therefore has ZERO headroom: the next
# type that method touches fails the build. That is deliberate — it is the one place in this
# repository where the ratchet is already tight.
CA1506(Type): 95
CA1506(Method): 40
